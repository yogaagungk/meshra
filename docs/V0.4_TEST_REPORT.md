# Meshra v0.4 — implementation and verification report

Date: **2026-10-19**, Linux/WSL2. Toolchain: Go **1.27.2**, Node **24.22.0**, npm **11.19.1**. The delivered application is the embedded
Developer Console, not a mockup. [API/UI discovery contract](API_UI_CONTRACT.md)
and [console guide, demo, migration and security model](V0.4_CONSOLE.md).

The native browser scenario uses **OMP, Codex and OpenCode**. Claude provider
verification remains waived by the operator's earlier instruction. No four-harness
native-success claim is made. All deterministic browser fixtures are isolated in
Go test code; no fake agents, messages, metrics or provider fallback are shipped.

## Browser, UX and accessibility checks

```sh
npx --prefix web playwright install chromium
# On this minimal Ubuntu environment, the required browser libraries were
# downloaded as .deb files and extracted under /tmp, without system changes:
# apt-get download libnspr4 libnss3 libasound2t64
LD_LIBRARY_PATH=/tmp/meshra-browser-libs/root/usr/lib/x86_64-linux-gnu \
  npm run test:e2e --prefix web
```

For a normal workstation, `playwright install --with-deps chromium` is the
standard prerequisite. The temporary LD_LIBRARY_PATH above is specific to the
verification environment.

**6 deterministic browser scenarios passed**; the native scenario correctly skips
without opt-in ([log](evidence/v0.4/browser-e2e.log)). They use Chromium against
the actual embedded Go HTTP server and SQLite, with explicitly named fixture
adapters in `tests/console_fixture_test.go`:

1. Multi-instance conversation creation, explicit targeted send, real persisted
   task state, reload while a fixture turn is running, sequenced snapshot/replay
   without duplicate groups, safe Markdown/code, pinned context and trace inspector.
2. Command shortcuts, same-harness IDs, theme persistence, responsive mobile
   panels, reduced motion, draft recovery and no horizontal overflow.
3. Private context denied for the receiving wallet identity before admission;
   offline queue/cancellation; retry disabled before explicit confirmation;
   approval-required native events represented as denied, with no invented Allow.
4. Every operations view against live registry/task/context records; publish text
   context and explicit reader grant through the UI; light theme and dialog access.
5. Keyboard-only creation (shortcut, title, search, checkbox, submit), focus access
   to the composer, IME Enter suppression, Shift+Enter newline and Ctrl+Enter send.
6. Touch-enabled mobile context: create/open chat, focus/type in composer, back
   to the inbox, navigate to Agents, and maintain viewport bounds.

axe-core WCAG 2 A/AA and 2.1 AA scans report **zero violations in sampled views**:
dark chat/inspector, light Settings, mobile inbox, all operations views, and the
light publish dialog and highlighted-code context preview. Keyboard focus, dialog Escape/focus behavior, mobile
visibility/overflow and touch are also asserted. This is not a certification or
an exhaustive manual screen-reader/assistive-device audit. Chromium touch emulation
does not replace testing every physical iOS/Android keyboard.

## Real cross-harness browser validation

A separately built **production Go executable** served an isolated private data
directory on `127.0.0.1:37732`. Native adapters came from normal daemon startup;
no fixture environment variable or alternate runtime was installed.

```sh
go build -o /tmp/meshra-v04-release ./cmd/meshra
# In a separate process, using a newly created private directory:
/tmp/meshra-v04-release --data-dir PRIVATE_STATE --addr 127.0.0.1:37732 serve

MESHRA_UI_NATIVE=1 \
MESHRA_UI_URL=http://127.0.0.1:37732/console/ \
MESHRA_UI_TEST_DIR=PRIVATE_STATE \
LD_LIBRARY_PATH=/tmp/meshra-browser-libs/root/usr/lib/x86_64-linux-gnu \
python3 scripts/measure-console.py --include-pid DAEMON_PID -- \
  npm run test:e2e --prefix web -- tests/native.spec.ts
```

`PRIVATE_STATE` was `/tmp/meshra-v04-release.pOdObN` and `DAEMON_PID` was `232481`
for the final run (temporary runtime identifiers, not deployment settings). The
actual browser test and machine-generated resource summary are preserved in
[native-browser-measured.log](evidence/v0.4/native-browser-measured.log); task
transitions are in [native-daemon.log](evidence/v0.4/native-daemon.log).

The browser registered and started unique OMP/Codex/OpenCode agents, published
an immutable contract and explicitly granted those readers, created a named
multi-agent channel, selected each exact recipient, attached version 1, and sent
three real model requests. Each model returned the approved marker **from the
attached context**; the request did not reveal that marker. The test observed a
running first turn before reload and verified the replayed result without a
duplicate task. All three tasks completed with `human:operator` origin, correct
recipient IDs, pinned refs, immutable result refs and inspectable correlation/
native session. The test passed in **37.3 s**; the measurement wrapper took
**39.447 s**. This proves browser-driven human-to-agent chat across three real
harnesses. It does not claim that models autonomously planned work or invoked
cross-harness MCP delegation, nor does it exercise tool-based workspace writes.

## Resource and storage observations

- WSL2 kernel: `6.18.54.1-microsoft-standard-WSL2`.
- Peak sampled aggregate RSS: **2,285,352 KiB (about 2.18 GiB)** across the browser
  test/Node/Chromium and separately supplied daemon/native process trees.
- Sampling: 100 ms; shared pages count once per process, so the sum is conservative;
  peaks shorter than the interval may be missed. Compilation and unrelated
  workloads are outside this tree measurement.
- End-of-scenario browser JavaScript heap: **15,557,408 bytes (about 14.8 MiB)**;
  DOM elements: **592**. These are measured, not budget promises.
- Frontend build: main JS **313.68 kB / 96.45 kB gzip**, Markdown chunk **158.41 /
  48.19 kB gzip**, query **43.26 / 13.40 kB**, primitives **43.50 / 14.77 kB**,
  CSS **54.01 / 11.27 kB**. Highlighting is lazy, **44.41 / 14.52 kB gzip**.
  The final build has no empty vendor chunk or oversized-chunk warning.
- Production has no Node/Vite process or remote font/CDN dependency.

The small representative run stayed below the requested 6 GB envelope. Native
provider/tool workloads and heavy parallel usage can differ; no universal memory
guarantee is made.

`TestConsoleThousandMessagePaginationAndBurstReplay` seeds **1,005 durable terminal
task records** in isolated SQLite, reads all of them exactly once across **26
40-item pages**, and drains all **1,005 events** through bounded 256-event cursor
batches without loss/duplication. That fixture is a storage regression, not 1,005
provider turns or a claim of rendering all messages at once. The UI deliberately
caps mounted history at eight pages and collapses long content. Browser scenarios
exercise pagination/reconciliation logic and real active snapshots at smaller
scale; they do not stress-test thousands of simultaneously expanded code blocks.

## Security and compatibility coverage

Dedicated tests verify same-origin login; rejection of agent-token escalation,
foreign Origin, invalid Fetch Metadata, forged Host and missing CSRF; HttpOnly/
SameSite/path cookie attributes; absolute expiry and logout revocation. Legacy
bearer APIs still reject browser Origin headers. Console administration never
changes an agent's identity/session mapping or bypasses recipient context ACLs.
Human-origin task deduplication, result refs, no synthetic agent registration,
partial multi-recipient admission, private context denial, owner-checked rename/removal with active-task guards, and feed replay are
covered by relay tests. The existing recovery, cancellation, uncertain-execution,
serialization and adapter protocol suites continue to pass under the race detector.

Schema 5 adds indexes transactionally; messages/results reuse the original task
store. Pre-existing migration rollback/idempotence tests still pass. The runbook
uses a stopped, complete pre-upgrade backup for rollback; it does not recommend
manually decrementing schema versions.

## Issues found, corrections and remaining limits

- Initial human-send tests exposed a key-scanner conflict when recipient IDs were
  appended to a literal browser idempotency key. Keys are now hashed with the
  conversation and exact recipient; repeats deduplicate and changed requests conflict.
- Chromium initially lacked `libnspr4`, `libnss3` and ALSA libraries. Extracting the
  official Ubuntu packages under `/tmp` enabled actual browser validation.
- axe detected 4.42:1 secondary-label contrast failures on selected dark inbox and light context rows. The faint tokens and theme-specific code-symbol palette were corrected; final scans pass without disabling that rule.
- One early native test was interrupted while waiting for a Chat link whose
  decorative arrow polluted its accessible name. Navigation now has explicit labels
  and decorative content is hidden from assistive names. No provider turn was
  admitted by that interrupted attempt. Subsequent real runs passed.
- Once browser specs were added, Vitest initially discovered them as unit tests. A dedicated Vitest include now keeps frontend units and Playwright specs in their proper runners; both pass separately.
- Participant-management coverage exposed legacy policy arrays serialized as null. The UI now handles null lists, and removal checks ensure a selected recipient is cleared without redirecting the draft to another agent.
- Final hardening bounded retained pages, preserved pending send keys/recipient
  choices across reload, prevented draft edits during admission from being lost,
  reset future replay cursors after restore, and removed an empty vendor chunk.

Limits are deliberate and visible: single trusted local operator, not multi-user
RBAC; no public hosting; no arbitrary browser terminal; no Allow approval API;
no live native typing/token animation; no safe agent identity/workspace editing;
no binary uploads; no full history sharing; no four-harness native assertion.
Changing context versions or revoking grants remains available through existing
API/MCP/CLI. Native side-effect cancellation/rollback cannot be guaranteed; uncertain
outcomes require inspection. Manual screen-reader testing, physical-device coverage
and large concurrent provider stress are not claimed. There are no fabricated
success indicators for these untested paths.
