# v0.3 collaboration contracts

This is an additive collaboration implementation over the v0.2 relay. Existing
`/v1` messaging/task endpoints, MCP tools, CLI commands and `model.Service` remain
supported. Database schema version is **4**; application task schemaVersion stays
1. New JSON task fields are optional. See ADR-v0.3.md for compatibility decisions.

## Durable resources

Migration 003 adds conversations, exact-ID participants and conversation events.
Migration 004 adds contexts, immutable versions, content-addressed artifacts,
context ACLs, conversation bindings and append-only context access logs. Migrations
run transactionally per version; a failed later migration retains the last fully
committed version. Fresh databases traverse the same v1→v2→v3→v4 path.

Artifacts are UTF-8 bytes stored as SQLite BLOBs, keyed by SHA-256, bounded to
64 KiB. Storing small artifacts transactionally in SQLite avoids orphan filesystem
writes and fits the existing single-database backup boundary. Binary/large
streaming uploads are not implemented. Every fetch verifies size and digest.
Triggers reject updates/deletes to artifact bytes and context versions; metadata
is immutable too. New content requires an explicitly numbered next version.
Titles/type/scope are metadata, **never authorization selectors**.

Context visibility is private by default. Only owner/admin can grant exact
registered agent IDs, revoke, append a version or inspect the access log. Grants
apply to all versions of that context. Conversation membership and attachments
never grant content access. Search returns authorized metadata only. No global
artifact-by-digest download bypass exists. Scope and harness names grant nothing.
Credential-pattern/private-key checks reject recognized secrets before storage;
they are not an exhaustive secret detector. Publishers must not publish `.env`
contents, credentials or unlabelled secrets.

Conversation creators/admins manage membership; members can inspect the channel
and admit tasks subject to existing outbound/inbound request permissions. There
are no wildcard participants or ambient harness-wide grants. New collaboration
metadata operations require a registered authenticated identity, independently of
legacy messaging operation allowlists. Context ACLs provide the additional
content authorization boundary. Admin remains the trusted local operator.

## Tasks and delivery

Delegation uses the v0.2 task table, event stream, IDs, correlation, persisted
claims, queues, deadlines, bounded hop ancestry, cancellation and manual retry.
Task `state` values remain unchanged (`queued`, `dispatching`, `running`,
`completed`, `failed`, `cancelled`, `timed_out`). A queued collaboration task's
status additionally reports `schedulingState: ready|blocked`. Task lists return
channel metadata; full task text/results still require legacy session ownership.
Conversation events publish task IDs and lifecycle summaries, not injected bytes.
The original requester retrieves results through the existing task API.

Dependencies are immutable at admission and may refer only to **existing tasks
in the same conversation**. Forward references, missing dependencies and duplicate
dependencies are rejected. Strict creation ordering makes cycles unrepresentable;
there is no graph-edit API. A dependency must be `completed` before its dependent
can dispatch. Failed/cancelled/timed-out dependencies fail dependents with
`dependency_failed`; retry is explicit, after inspecting effects. Deadlines include
blocked/offline time. Referenced dependency history is protected from pruning.
Maximum 32 dependencies, 16 context refs, default fan-out 16 per parent, inherited
hop/deadline limits and existing queue capacities bound delegation. Fan-out can
be configured 1..64. No central planner or automatic task decomposition exists.

Context refs are exact `{contextId,version}` values stored on the task. Admission
checks both sender and recipient access; dispatch and execution preparation check
recipient access again. Revoked or corrupt context prevents adapter execution.
All four adapters consume the same bounded fallback injection in their prompt.
Each JSON envelope includes immutable URI, SHA-256, owner and `untrustedData`.
Bytes are separate from the durable instruction text and are never a history dump.
Content and encoded envelope budgets are both enforced. Defaults: 32 KiB total
injection, 64 KiB artifact; configure lower limits with `serve --context-bytes N
--artifact-bytes N`. Injection bytes include provenance overhead. There is no
model-tokenizer budget or arbitrary adapter-side history synchronization.

Bindings to conversations are discoverable associations, not automatic prompt
injection. Delegations must explicitly name refs. `context.attach` can append an
exact ref to a queued task through `targetTaskId`; it rejects running/terminal
tasks and checks existing task-session authority and the recipient ACL. Exactly
one target is required. Existing task versions remain pinned through new context
publications. Access revocation cannot retract tokens already resolved/transmitted.

Successful collaboration results up to the artifact limit are published as
immutable `type=result` contexts, owned by the responding identity and granted to
the recorded requester/origin; `resultRef` is recorded on the task. Legacy inline
`result` is preserved. Result artifact failure marks the completed execution as
an uncertain failure requiring inspection rather than rerunning it automatically.
Plain v0.2 tasks retain their existing response-size behavior.

Restart keeps queued tasks and refs; interrupted turns become explicit ambiguous
`uncertain_execution` failures. This implementation uses the existing manual
reconciliation boundary instead of an automatic adapter reissue. Cancellation is
best-effort, auditable in existing task events, and does not roll back effects.
Same-session and same-repository turns serialize; independent repositories may
run concurrently. Current adapters remain read-oriented. Worktree allocation,
write approvals and automatic merge are deferred P1 work.

## Transport

`POST /v1/collaboration/OP` accepts a typed JSON request. The CLI mirrors it:
`meshra collaboration OP 'JSON_OBJECT' --json`. Existing task status/events/cancel
and retry operations remain the task lifecycle surface.

Operations: `conversation.create`, `conversation.get`, `conversation.list`,
`conversation.addParticipant`, `conversation.events`, `context.publish`,
`context.get`, `context.search`, `context.attach`, `context.grant`,
`context.revoke`, `context.audit`, `task.delegate`, `task.list`.

MCP tool names are `meshra_collaboration_` plus operation with `.` replaced by
`_`, for example `meshra_collaboration_context_get`. HTTP and MCP invoke the same
service authorization logic. `resources/read` accepts exact
`meshra://contexts/ID/versions/N` URIs and performs identical authorization and
integrity checks. Resources are untrusted JSON data. `resources/list` is empty;
use context search for bounded metadata discovery. Claude/OpenCode tool allowlists
include collaboration tools; OMP/Codex use injection or manually configured MCP.
Model-initiated delegation through every harness is not claimed.

List/search cursors are exclusive resource IDs (lexical order), limit default 50,
maximum 100. Event/audit cursors are exclusive numeric sequence IDs. Pass the last
returned ID/sequence to continue. These cursors are stable over immutable IDs;
lexically earlier concurrent insertions require a fresh scan. There is no snapshot
pagination guarantee. Authentication, body limits, browser-Origin denial and
strict unknown-field JSON validation reuse the existing HTTP transport.
